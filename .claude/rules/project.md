# 프로젝트 공통 규칙

CDRI 프론트엔드 사전과제 — 카카오 책 검색 API 기반 도서 검색 서비스.
요구사항·디자인 토큰·작업 순서는 `docs/PLAN.md`가 기준이다.

## 작업 방식

- 작업은 `docs/PLAN.md` "5. 작업 순서"의 Step 단위로 한다. 현재 Step 범위 밖의 기능은 만들지 않고, 필요해 보이면 사용자에게 제안만 한다.
- **설계 결정은 사용자가 한다.** 데이터 구조, 상태 관리 방식, 공개 인터페이스(컴포넌트 props 설계 포함), 라이브러리 선택, 폴더 구조 변경은 선택지와 장단점을 보여주고 사용자가 고른 뒤에 구현한다. 결정은 `docs/adr/`에 기록한다. (`/adr`)
- 이미 채택된 ADR과 다르게 구현해야 하면 멈추고 사용자에게 알린다.
- 디자인에 명시되지 않은 동작은 지원자 판단에 맡겨져 있다. 판단이 필요하면 추천안과 근거를 사용자에게 보여주고, 결정되면 ADR과 README "강조하고 싶은 기능"의 소재로 남긴다.
- Step은 `step-<번호>-<영문-이름>` 브랜치에서 작업하고 PR로 main에 합친다.
- 커밋 메시지: `<type>(step-N): <한국어 요약>`. type은 `feat`, `fix`, `test`, `docs`, `style`, `refactor`, `perf`, `chore`. Step 밖의 커밋은 scope 없이 `<type>: <한국어 요약>`. 본문이 필요하면 무엇을·왜 바꿨는지 한국어로 쓴다. 형식과 예시는 `docs/PLAN.md` "작업 흐름"을 따른다.
- 커밋은 사용자가 요청할 때, 또는 `/step-start`로 시작한 Step 작업 중(단위마다)과 `/step-finish`에서 한다. push와 PR은 사용자가 요청할 때만 한다. (`/pr`)
- 최신 버전 라이브러리(Vite, React Router, TypeScript, TanStack Query, Tailwind)의 사용법은 학습 때 알던 것과 다를 수 있다. 설정이나 API를 쓰기 전에 context7이나 `node_modules`의 문서로 설치된 버전을 확인한다.

## 설명 방식

- 사용자에게는 한국어로, 쉬운 말로 설명한다. 전문 용어를 쓰면 한 줄로 뜻을 붙인다.
- 과제 안내에 "AI가 작성한 코드를 이해 없이 제출하지 말 것"이 있다. 핵심 코드는 왜 그렇게 짰는지 사용자가 설명할 수 있도록 근거를 함께 알려준다.

## 디자인

- 색상과 글자 스타일은 `@theme`에 정의한 Figma 토큰만 쓴다. `text-[#353C49]`, `text-[14px]` 같은 임의 값은 쓰지 않는다. 토큰에 없는 값이 필요하면 Figma 실측값을 확인하고 토큰을 추가한다.
- 책 표지 이미지는 API `thumbnail`을 쓴다. Figma 시안의 책 표지 이미지는 내보내지 않는다.
- Figma 접근: REST API (`FIGMA_TOKEN`은 `~/.zshrc`). 파일 키와 화면별 노드 ID는 `docs/PLAN.md`를 본다.

## 보안

- API 키는 `.env`(`VITE_KAKAO_REST_API_KEY`)에서만 읽는다. 코드·테스트·문서에 키 값을 적지 않는다.
- `.env`는 커밋하지 않는다. 키 이름만 담은 `.env.example`을 커밋한다.
- Figma 토큰은 프로젝트 안 어디에도 두지 않는다. (`.env`는 평가자에게 이메일로 전달되는 파일이다)

## 완료 조건

- 작업이 끝났다고 말하기 전에 `pnpm typecheck`, `pnpm lint`, `pnpm test`를 실행하고, 실패하면 결과를 그대로 보고한다. (Step 1 이후)
- 버그를 고치면 그 버그를 다시 잡는 테스트를 추가한다.
