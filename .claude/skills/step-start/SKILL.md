# Step 시작: Step $ARGUMENTS

## 1. Step 내용 확인

- `docs/PLAN.md` "5. 작업 순서"에서 `### Step $ARGUMENTS.` 섹션의 체크리스트를 읽는다. 체크리스트 전체가 이 Step의 완료 기준이다.
- "3. 기능 요구사항"에서 이 Step과 관련된 항목도 함께 읽는다.
- 앞 Step 제목에 ✅가 있는지 확인한다. 없으면 사용자에게 알리고 계속할지 묻는다.
- `docs/adr/`의 기존 ADR을 훑어서 이번 Step이 따라야 할 이전 결정을 파악한다.
- 화면 작업이 있는 Step이면 관련 Figma 노드를 REST API로 읽어 실측값(간격, 크기, radius)을 확인한다.

## 2. 브랜치 만들기

- 작업 트리가 깨끗한지 `git status`로 확인한다. 변경이 있으면 멈추고 사용자에게 묻는다.
- `main`으로 이동해 원격과 맞춘다. (`git switch main && git pull --ff-only`) 앞 Step PR이 아직 머지되지 않았으면 사용자에게 알린다.
- `main`에서 `step-<번호>-<짧은-영문-이름>` 브랜치를 만든다. (예: `step-4-book-search`)

## 3. 결정할 것 뽑기

이 Step에서 **사람이 결정해야 하는 설계 선택**을 목록으로 만든다. 각 항목에 선택지 2~3개와 장단점을 짧게 붙인다.

- 예: 컴포넌트 분리 단위, props 설계, 상태를 URL/store/컴포넌트 중 어디에 둘지, 라이브러리 선택
- `docs/PLAN.md` "4. 결정 필요 사항"에 아직 ☐인 항목 중 이 Step에 걸리는 것도 포함한다.
- 결정은 사용자가 한다. 추천은 해도 되지만 사용자가 고르기 전에 구현하지 않는다.
- 결정되면 `/adr`로 기록한다.

## 4. 작업 계획

아래 형식으로 사용자에게 보여주고 확인받은 뒤 구현을 시작한다.

```
Step N: <제목>
완료 기준: <PLAN.md의 체크리스트>

결정할 것:
  1. ...

작업 순서: (번호마다 끝나면 커밋)
  1. ...

테스트:
  - 단위 테스트: ...
  - 브라우저 테스트: ... (화면 변경이 있을 때만. PR 영상으로도 쓰인다)
```

## 지킬 것

- `.claude/rules/`의 규칙을 따른다. (디자인 토큰만 사용, API 키 취급, 테스트 규칙)
- 작업 중간중간에 커밋한다. 이 스킬로 시작한 Step 브랜치에서는 사용자가 따로 말하지 않아도 된다.
  - 작업 순서의 한 단위가 끝날 때마다 커밋한다. 끝에 한 번에 몰아서 커밋하지 않는다.
  - 커밋 전에 `pnpm typecheck`, `pnpm lint`, `pnpm test`가 통과해야 한다. 실패하면 커밋하지 않고 결과를 보고한다.
  - 메시지는 `feat(step-N): ...`, `fix(step-N): ...`, `test(step-N): ...`, `docs(step-N): ...`처럼 쓴다.
  - push와 PR은 여전히 사용자가 요청할 때만 한다.
- 작업한 항목은 `docs/PLAN.md` 체크리스트에 `[x]`로 표시한다.
