# 0050. 검색 기록은 검색을 실행할 때마다 맨 앞에 넣고, 탭 사이에도 맞춘다

- 상태: 채택
- 날짜: 2026-11-27
- 관련 Step: Step 6, Step 8

## 배경
Figma 요구사항은 검색 기록을 최대 8개 두고, 넘치면 오래된 것부터 지우고, 브라우저를 다시 열어도 유지하는 것이다. 저장은 Zustand + persist로 하고([0005](0005-client-state-zustand.md)), 전체 검색만 저장한다([0004](0004-search-history-scope.md)).
언제 기록에 넣는지, 무엇을 같은 검색어로 보는지는 시안에 없다. 또 persist는 탭 여러 개를 맞춰 주지 않아서, 마지막에 저장한 탭이 다른 탭의 기록을 덮어쓴다.

## 선택지
- 저장 시점
  - A안 검색 실행마다: Enter, 기록 클릭 때마다 넣고 같은 검색을 다시 실행해도 맨 앞으로 / 오타 검색도 남음
  - B안 URL이 바뀔 때만: 지금 `submit` 구조 그대로 / 뒤로가기로 돌아간 검색어로 다시 Enter를 쳐도 순서가 그대로
  - C안 결과 1건 이상일 때만: 오타가 안 쌓임 / 응답 뒤에 저장해야 해서 `SearchResults`까지 연결
- 중복 기준: 앞뒤 공백 제거 후 완전 일치 / 대소문자 무시(어느 표기를 남길지 규칙 추가)
- 연결 위치: `useSearchInput` 안 / `SearchPage`에서 store와 훅을 따로 연결(검색 흐름이 두 곳에 나뉨)
- 탭 동기화: `storage` 이벤트로 다시 읽음 / 안 함(다른 탭 기록이 덮여 사라짐)
- 테스트: 메모리 저장소로 store 직접 / 규칙만 순수 함수로 분리(저장·복원은 단위 테스트 불가)

## 결정
모두 첫 번째 안. (사용자 선택)
- 사용자가 검색을 실행할 때만 넣는다. 결과가 0건이거나 에러가 나도 넣는다. 뒤로가기, 새로고침, 공유받은 링크로 들어온 검색은 사용자가 실행한 것이 아니어서 넣지 않는다.
- 앞뒤 공백을 지운 글자가 완전히 같으면 같은 검색어다. 새로 넣지 않고 맨 앞으로 옮긴다. 검색어가 목록 key로도 쓰여서 중복이 없어야 한다.
- `useSearchInput`이 `submit`에서 기록에 넣고, 기록 항목용 `searchKeyword(keyword)`를 돌려준다. 이 함수는 입력창을 채우고 바로 검색한다. 검색 흐름은 이 훅 한 곳에 있다([0049](0049-search-page-split.md)).
- 다른 탭이 localStorage를 바꾸면 브라우저가 보내는 `storage` 이벤트를 받아 store를 다시 읽는다. Step 8 찜 store도 같은 방식을 쓴다.
- Vitest는 Node 환경이고, Node 26은 `--localstorage-file` 없이는 localStorage를 쓸 수 없다. 그래서 테스트에서 메모리 저장소를 그 자리에 넣고 `getState()`로 확인한다. 새로고침 뒤에도 남는지는 Playwright로 한 번 더 확인한다.

## 결과
- 기록에는 사용자가 직접 실행한 검색만 남는다. 오타 검색은 X로 지워야 한다.
- `Harry`와 `harry`는 다른 항목으로 남는다.
- 탭 두 개에서 각각 검색해도 기록이 사라지지 않는다.
- 단위 테스트가 persist의 저장·복원까지 확인한다. 추가 의존성은 없다.
